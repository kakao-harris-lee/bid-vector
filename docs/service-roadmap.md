# 서비스 로드맵 (bid-vector)

> 이 문서는 운영자가 정리한 0~3단계 로드맵을 **현재 코드 구현 상태와 대조**해 보강하고,
> 단계별 수용 기준·교차 워크스트림·리스크를 추가한 단일 출처 로드맵입니다.
> 기획 매핑은 `docs/first_plan_implementation_review.md`, 운영 원칙은 `AGENT.md`,
> 프론트 확장은 `docs/web-development-plan.md`를 함께 참고하세요.
>
> 최초 작성: 2026-06-04. 현재 main 기준 구현 상태를 코드 조사로 검증해 반영함.

---

## 0. 가이딩 원칙 (전 단계 공통)

1. **업체 정보 정확도 > AI 모델.** 추천 품질을 좌우하는 1순위는 예측 모델이 아니라
   업체 정보(면허·지역·공사가능금액·실적·선호/제외)의 정확도다. 모든 단계에서 이 5축이
   실제 매칭/추천에 반영되는지 우선 확인한다.
2. **데이터 해자(moat)는 "축적된 실제 개찰 결과".** 추천이 맞았는지 검증·학습하려면
   개찰 결과를 자동으로 수집·정합하는 파이프라인이 핵심 자산이다.
3. **범위 고정 — "공사 입찰 중소업체" 한정.** 기능을 넓히기보다 한 도메인에서 깊게.
   (운영자 원안의 핵심 직관, 유지.)
4. **증적 기반으로 진행.** 단계 전환은 "느낌"이 아니라 측정된 KPI와 산출물로 판단한다.
   → KPI를 측정할 **계측(telemetry)** 이 없으면 KPI는 목표가 아니라 희망이다 (교차 워크스트림 C-1).
5. **현재 구현이 기획보다 우선.** 충돌 시 호환 가능한 중간 단계부터.

## 1. 현재 구현 상태 요약 (2026-06-04, main 기준)

코드 조사 결과 단계별 완성도. (✅ 완료 · ⚠️ 부분 · ❌ 미구현)

| 단계 | 완성도 | 한 줄 평 |
|---|---|---|
| **0단계 — 안정화** | ✅ 약 90% | 수집→분류→예측→알림→버튼응답 end-to-end가 실데이터로 동작. 남은 건 *빌드*가 아니라 *운영 검증·증적 수집*. |
| **1단계 — 단일 업체 MVP** | ✅ 약 85% | 최근 작업(프로필 편집·프로필 인지 매칭·건설 면허 매칭·참가 사유 표시)으로 기능 대부분 완성. 남은 건 시공능력 모델링 + KPI 계측 + 실제 업체 투입. |
| **2단계 — 실증 고도화** | ⚠️ 약 60% | 예측 정확도 추적·피드백 보정·threshold 조정은 됨. **개찰 결과 자동 추적**과 **공사 특화 리스크**가 핵심 공백. |
| **3단계 — SaaS 전환** | ⚠️ 약 30% | 단일 운영자 모델이 견고(= 멀티테넌트로 깨야 함). JWT 인증만 있고 RBAC·과금·온보딩·월간 리포트 부재. synthetic 다중 operator가 디딤돌. |

> 결론: **0~1단계는 "거의 다 만들어져 있다."** 진짜 일은 *만드는 것*보다 *실제 업체에 붙여
> 측정·검증하는 것*이다. 2단계의 개찰 자동 추적과 공사 도메인 모델이 다음 빌드의 핵심이고,
> 3단계 SaaS는 **2단계 가치 검증 전에 시작하지 말 것**(아래 게이트 G-3).

## 2. 단계별 로드맵 (보강판)

각 단계: **목표 / 현재 상태 / 남은 작업 / 수용 기준(Exit Gate)**.

### 0단계 — 현재 코드 안정화 → *운영 검증·증적*

**목표:** "개발된 기능이 실제 환경에서 한 사이클 돈다 + 증적이 남는다."

**현재 상태 (코드 근거):**
- ✅ KONEPS 실수집: `app/services/koneps/collector.py` — OpenAPI(koneps/scsbid) 1차 + 크롤 fallback, `Project`/`HistoricalData`/`TenderResult` 적재, `collect_koneps_notices` Celery 태스크 + beat.
- ✅ Telegram: 송신(`telegram.py`) + 폴링(`poll_telegram_updates`, 현재 .env에서 ENABLED) + webhook + 발신자 인가 게이트(PR #53). 인바운드 버튼/명령으로 의사결정.
- ✅ Smoke test: `app/services/smoke_test.py` + 일일 스케줄(PR #49, `SMOKE_TEST_SCHEDULE_ENABLED`, 기본 OFF). 수집→예측→Telegram 4단계 phase.
- ✅ 대시보드: `app/api/dashboard.py`(`/summary`에 crawl_success_rate·notification 집계) + 프론트 HomeScreen/Opportunities/Results.
- ✅ 실패 증적: `CrawlJob`(status/error_message/result_count), `Notification`, `app/services/analytics_reporting.py`.

**남은 작업:**
- [ ] **smoke 스케줄 활성화**(`SMOKE_TEST_SCHEDULE_ENABLED=true`) 후 며칠 자동 사이클 관찰. (Telegram 폴링은 이미 ON.)
- [ ] **smoke 리포트 산출물 영속·조회**: phase별 PASS/FAIL, 수집 성공률, 추천 공고 수, 알림 성공률을 한 곳에서 보는 운영 리포트(현재는 로그/개별 모델에 흩어짐).
- [ ] 예측/추천 API 응답 샘플 캡처(증적 보관).

**수용 기준(Exit):** 운영 smoke 리포트가 N일 연속 green이고, 수집 성공률·추천 수·알림 성공률이 한 화면/리포트로 확인 가능.

### 1단계 — 단일 업체 실증 MVP

**목표:** "한 공사 중소업체가 실제 입찰 업무에 매일 쓴다."

**대상:** 공사 분야 중소업체 1곳, 운영자 1명, 실제 업체 프로필.

**현재 상태 (코드 근거):**
- ⚠️ **업체 프로필 등록**: `CompanyProfile`(면허/지역/업종/연매출/역량/실적) + 프론트 `features/profile/CompanyInfoEditor`(PR #51) — 면허·지역·업종·연매출·실적·역량 + 참여 예산범위·선호/제외를 한 화면에서 편집. **단일 폼(마법사 아님).** **시공능력평가액/도급한도 전용 필드 없음**(annual_revenue·capacity_score 프록시).
- ✅ **맞춤 추천 + 참가 가능/불가 사유**: classifier 6축(업종/면허/지역/예산/역량/시맨틱) + 건설 면허 매칭(PR #52) + `opportunity_analysis`의 strengths/risk_flags + `DecisionReasonsCard`(왜 가능/왜 위험/판단, PR #54~56). 백테스트도 프로필 인지(PR #50).
- ✅ **투찰 후보가 추천**: `app/ai/` predictor 3종 + 자동 선택 + guardrail(낙찰하한), 시나리오별 추천가, paper bidding.
- ✅ **알림 + 투찰 여부 기록**: `BidDecisionRecord`(action/decision_status/reasoning), Telegram 콜백 동기화.

**남은 작업:**
- [ ] **시공능력 도메인 필드 추가**: `construction_capacity_amount`(시공능력평가액)·`awarded_contract_limit`(도급한도) 등 신규 컬럼 + 매칭 반영(예산/역량 평가에 사용). → 공사 매칭 정확도의 핵심.
- [ ] **등록 마법사 UX**: 단일 폼 → 단계형 온보딩(면허→지역→능력→선호) 마법사. 신규 업체가 막힘 없이 정확히 입력하도록.
- [ ] **KPI 계측(필수, 교차 C-1)**: 공고 검토 시간, 놓친 유효 공고, 검토 가치 비율, 수동 수정 횟수 — 현재 *측정 수단 없음*. 이벤트 로깅 없이는 1단계 KPI 검증 불가.
- [ ] 코드 마스터(KONEPS 업종/지역/면허) 드롭다운으로 자유텍스트 오입 제거(선택).

**KPI:** 공고 검토 시간 70%↓ · 놓친 유효 공고 감소 · 추천 중 검토 가치 60%↑ · 매일 확인 가능한 대시보드.

**수용 기준(Exit):** 실제 업체 1곳이 2~4주간 매일 사용 + 위 KPI를 *측정값*으로 제시.

### 2단계 — 실증 고도화

**목표:** "추천이 맞는지, 투찰가가 도움이 되는지 데이터로 검증한다."

**현재 상태 (코드 근거):**
- ✅ 사정률(예가 대비) 예측 성능 추적: `PricePrediction.backtest_average_absolute_error_rate`, `predictor_backtest.py`, historical_backtest 자동 스케줄(누적).
- ✅ 피드백 보정 + threshold 조정: `prediction_feedback.py`(실제/예측 비교 보정), `OperatorStrategy` bid_now/review_threshold, `decision_analytics` 퍼널.
- ⚠️ **개찰 결과 추적**: `TenderResult`·`PaperBidSettlement` 모델은 있으나 **개찰 결과 자동 수집 태스크 부재** — 현재 백테스트/수동 연결 위주. (win rate는 "가격 기준 추정 낙찰" 프록시 — caveat 유지.)
- ❌ **공사 특화 리스크**: 공동도급/지역의무공동도급/지역가산점/유사실적이 매칭·사유에 **미반영**(classifier에 해당 로직 없음).

**남은 작업:**
- [ ] **개찰 결과 자동 추적 파이프라인(최우선)**: `collect_tender_results()` 류 Celery 태스크 + 스케줄로 개찰 결과를 자동 수집 → `TenderResult`/`PaperBidSettlement` 정합 → 추천 vs 실제, paper vs 실제 개찰을 *자동* 비교. → 데이터 해자.
- [ ] **공사 특화 리스크 모델링**: 공동도급(지역의무공동도급)·지역가산점·유사공사 실적 요건을 분류/사유에 반영. "투찰 위험 요소", "공동도급/실적/면허 리스크" 사유 강화.
- [ ] 추천 false positive/negative 라벨 수집 루프(운영자 피드백 → 학습 데이터).
- [ ] 업체별 전략 threshold 자동 튜닝 제안(현재 수동 조정).

**KPI:** 추천 정확도 · 실제 투찰 전환율 · 투찰 후 개찰결과 추적률 · 추천가-실제낙찰가 차이 · 수동 수정 횟수↓.

**수용 기준(Exit·게이트 G-3):** 개찰 결과가 자동 추적되어 *실측* 추천 정확도/투찰가 오차가 산출되고, 1~3개 실제 업체에서 "쓸 만하다"가 데이터로 증명됨. → 이게 충족돼야 3단계(SaaS) 착수.

### 3단계 — 공사 입찰 특화 SaaS 전환

**목표:** "중소 공사업체용 SaaS로 전환." **범위 고정: "공사 입찰 중소업체"** (원안 유지).

**현재 상태 (코드 근거):**
- ✅/⚠️ **멀티테넌트 준비도**: 현재 *의도적으로* 단일 운영자(`CompanyProfile.user_id`/`OperatorStrategy.user_id` unique, `single_user.ensure_operator_account` canonical). SaaS는 이 가정을 깨야 함 → 테넌시·데이터 격리 필요. legacy `allocations` 다중 배분 흔적 잔존.
- ✅ **디딤돌**: synthetic 다중 operator 인프라(`synthetic_custom_operator.py`, operator별 profile/strategy upsert·조회 패턴)가 멀티테넌트 코드 시드로 활용 가능.
- ⚠️ **인증/과금/리포트**: JWT 발급(`auth.py`)은 있으나 RBAC(역할)·과금/구독 모델·온보딩 흐름·월간 리포트 생성 **전무**(`is_admin` 플래그만).

**남은 작업:**
- [ ] **멀티테넌트 아키텍처(최대 비용)**: user_id unique 해제 + 테넌트별 데이터 격리, canonical operator 가정 제거, KONEPS 수집은 공용/테넌트별 rate-limit 관리. → 단일→다중은 *대공사*. G-3 통과 후 착수.
- [ ] **RBAC + 온보딩 마법사**(1단계 등록 마법사를 테넌트 셀프서비스로 확장).
- [ ] **과금/구독 도메인** + 요금제 게이팅.
- [ ] **월간 성과 리포트** 생성(decision_analytics 퍼널을 리포트로 패키징).
- [ ] 공고 상세 AI 요약 · 투찰 이력 관리 · 개찰 결과 자동 추적(2단계 산출물 재사용).

**요금제 ↔ 현재 기능 매핑:**
| 티어 | 기능 | 현재 |
|---|---|---|
| **Lite** | 공고 추천/알림 | ✅ 대부분 구현 |
| **Pro** | 공고 분석/투찰가 추천 | ✅ 대부분 구현 |
| **Expert** | 실증 리포트/전략 튜닝/컨설팅 | ⚠️ 리포트·자동 튜닝 빌드 필요 |

→ Lite/Pro는 기존 기능으로 거의 패키징 가능. Expert는 2단계 산출물(개찰 추적·리포트)에 의존.

## 3. 교차 워크스트림 (단계에 걸친 필수 작업)

- **C-1. 계측/관측(telemetry).** 1~2단계 KPI(검토 시간·정확도·전환율·수동 수정)는 현재 *측정 불가*.
  사용자 행동/추천 결과 이벤트 로깅 + KPI 집계 대시보드를 1단계와 **병행** 구축. *이것 없이는 모든 KPI가 무의미.*
- **C-2. 공사 도메인 모델.** 시공능력평가액·도급한도(1단계), 공동도급·지역의무·지역가산·유사실적(2단계).
  이 도메인 정확도가 "공사 특화" 차별점의 본질. 단계 가로지름.
- **C-3. 개찰 결과 데이터 파이프라인.** 2단계 핵심이자 학습/리포트/Expert 티어의 토대. 자산화.
- **C-4. 컴플라이언스.** KONEPS 크롤 ToS·rate limit(OpenAPI 우선, sleep), 투찰가 추천의 *조언/면책*
  포지셔닝(도구는 제안, 결정은 운영자), 멀티테넌트 사업자정보/개인정보. 3단계 전 정리.

## 4. 리스크 레지스터

| 리스크 | 영향 | 완화 |
|---|---|---|
| KONEPS API/사이트 변경·ToS | 수집 중단 | OpenAPI 우선 경로 유지, 크롤은 fallback·저빈도, 변경 감지 알림 |
| 예측/추천 신뢰도가 "투찰가를 믿을" 수준에 못 미침 | 핵심 가치 훼손 | 2단계 실측 정확도 게이트, guardrail 유지, "조언" 포지셔닝 |
| 단일 실증 업체 의존 | 일반화 실패 | 2단계에서 1→3개 업체로 확장 후 SaaS |
| **2단계 검증 전 SaaS 착수** | 멀티테넌트 대공사 매몰비용 | **게이트 G-3 강제**: 실측 가치 증명 전 3단계 금지 |
| 공사 도메인 미반영(공동도급/시공능력) | 공사업체에 "안 맞는" 추천 | C-2 우선 투자 |
| KPI 미계측 | 진척/가치 입증 불가 | C-1을 1단계와 병행 |

## 5. 제안 요약 (원안 대비 추가·변경점)

1. **0~1단계 재프레이밍**: 대부분 *이미 구현됨*. 0단계는 "빌드"가 아니라 **운영 검증·증적**,
   1단계는 "기능 개발"이 아니라 **실제 업체 투입 + KPI 측정**으로 본다.
2. **계측(C-1)을 1단계와 병행 추가**: KPI를 측정할 수단이 없으면 1~2단계가 검증 불가. *가장 중요한 누락.*
3. **시공능력 도메인 필드를 1단계로 승격**: 원안 1단계 "시공능력"은 현재 전용 필드가 없음(프록시뿐).
   공사 매칭 정확도 직결 → 명시적 빌드 항목.
4. **개찰 결과 자동 추적을 2단계 최우선 + 데이터 해자로 명시**: 현재 수동/백테스트뿐. 자산화.
5. **공사 특화 리스크(공동도급/지역의무/지역가산/유사실적)를 명시적 2단계 항목으로**: 현재 미구현이며
   "공사 특화 SaaS" 차별점의 핵심.
6. **G-3 게이트 신설**: 2단계 실측 가치 증명 전 3단계 SaaS 착수 금지. 멀티테넌트는 단일→다중 *대공사*임을 명시.
7. **요금제↔기능 매핑**: Lite/Pro는 기존 기능으로 거의 패키징 가능, Expert만 2단계 산출물 의존 — 단계 의존성 명확화.
8. **컴플라이언스(C-4)**: 투찰가 추천의 조언/면책 포지셔닝·KONEPS ToS·멀티테넌트 정보보호를 3단계 전 정리.

---

## 6. 단계 의존성 한눈에

```
0단계(운영 검증·증적)  ── 거의 완료, smoke 활성화+리포트만
   │
1단계(단일 업체 MVP)   ── 기능 ~85% 완료
   ├─ + 시공능력 필드(C-2)
   ├─ + 등록 마법사
   └─ + KPI 계측(C-1)  ←★ 병행 필수
   │
2단계(실증 고도화)
   ├─ + 개찰 자동 추적(C-3)  ←★ 데이터 해자
   ├─ + 공사 리스크 모델(C-2)
   └─ + 피드백 라벨 루프
   │  ════ 게이트 G-3: 실측 가치 증명 ════
3단계(SaaS)
   ├─ 멀티테넌트(대공사) + RBAC
   ├─ 과금/온보딩
   └─ 월간 리포트/Expert (C-3 재사용)
```
